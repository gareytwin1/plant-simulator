How to read this plan

This page is the source of truth for what gets built, in what order, on which branch, and by whom. Set a status on any task and it persists for everyone.

The organizing idea: one spine, many satellites. A handful of tasks rewrite the same central files — the equipment base class, the simulation engine, the plant topology, the network solver. Those are the spine. They must run sequentially, owned by one agent at a time, because two agents cannot independently redesign the same core architecture without producing an unmergeable mess.

Everything else is a satellite: a new module in its own directory that depends only on a written contract, never on the spine's internals. A PID block, an alarm state machine, a ring-buffer historian, an envelope evaluator — each is a pure algorithm that can be built and fully tested against a fake process before the real plant exists. Satellites parallelize freely.

The gate for parallel work is contracts, not code. The eight interface contracts below must be written down and merged before satellite branches open. Once they exist, thirteen branches can start on day one.

Independent

New module, own directory, depends only on a frozen contract. Hand to an agent immediately. Merges without coordination.

Dependent

Also isolated, but waits on a specific upstream task. The dependency chips on each task turn green as blockers clear.

Core

Touches shared architecture, plant state, or plant-wide physics. Stays on the main development path. One owner at a time.

Version 1 scope

ships 18 December 2026

Thirteen weeks buys one small plant built properly, not one large plant built badly. Version 1 exists to prove the architecture and the gameplay loop end to end; the olefins plant is then grown by adding equipment and sections to a foundation that already works.

The V1 bet: a complete small plant beats a partial large one. Every architectural idea in this plan — the equipment contract, the network solver, envelopes, alarms, trips, scenarios, scoring — is exercised by a seven-device train just as thoroughly as by a cracking complex. What a bigger plant adds is more instances, not more mechanisms. Instances are cheap to add after the release; mechanisms are not.

So the V1 cut line is drawn by mechanism, not by equipment count: anything that proves a new mechanism is in, and anything that is a second example of a mechanism already proven is deferred.

Architecture proven

One equipment contract driving devices the engine has never seen. Plant loaded from configuration, not code. Server-owned clock, fixed timestep, bit-identical replay from a seed.

Process proven

One plant-wide pressure-flow solution. Level that accumulates and pushes back on hydraulics. Temperature that propagates. Mass balance that closes over ten thousand steps.

Operator layer proven

Envelopes with tracked excursion time, alarms that name symptoms, at least one real trip with a recovery window, two PID loops with auto/manual and bumpless transfer, trends to diagnose from.

Game loop proven

Six or more authored upsets with hidden causes, objectives, recovery detection, deterministic replay, a scored debrief — and a structural test proving the game layer cannot reach into the physics.

Shipping proven

Running on a machine that is not yours, behind CI, with validated input, structured logs, a health endpoint and documentation someone else can follow.

The release test

A person who has never seen the code loads a scenario, misdiagnoses it, trips the plant, reads the debrief, and wants to try again. If that works, V1 is done.

Deferred past Version 1

Not cancelled — sequenced. Each of these is a second instance of a mechanism V1 already proves, or a feature that only pays off once single-player training is solid. Leaving them out is what makes the date credible.

Interface contracts

freeze before parallel work

These eight definitions are what let separate agents work without reading each other's code. Write them, merge them, then treat them as fixed — a change to any of them after Checkpoint A invalidates in-flight satellite branches, so changes go through the spine owner.

C1Equipment contractapp/equipment/base.py

Every device implements this and nothing more. The critical rule: equipment never reads or writes node pressures. Today GasCompressor owns supply_pressure and discharge_header_pressure and solves its own operating point. In a connected plant those are solver outputs. A device publishes a curve; the solver finds where it lands.

class Equipment:
    tag: str                      # "K-101", "P-101", "FV-1023"
    ports: dict[str, Port]        # {"suction": Port, "discharge": Port}

    def integrate(self, dt: float) -> None:
        """Advance SLOW state only: load ramp, valve stroke,
        level, metal temperature. Never touches flow/pressure."""

    def characteristic(self, flow: float) -> float:
        """Pressure change across the device at this flow.
        Positive = rise (machine), negative = drop (valve, pipe)."""

    def get_state(self) -> dict:   # flat, JSON-safe primitives
    def reset(self) -> None:       # back to construction state
C2Topology: node, branch, streamapp/plant/topology.py

The graph the solver walks. A node is a pressure point; a branch carries flow between two nodes and holds exactly one device; a stream is the material state the branch carries.

Node(id, pressure, is_boundary, elevation)
Branch(id, from_node, to_node, device, flow)
Stream(flow, pressure, temperature, composition)

Boundary nodes hold pressure fixed — they are the plant's battery limits. Every topology needs at least one.

C3Plant configuration schemaconfig/plants/*.yaml

Adding equipment must stop requiring a code change. This schema is the boundary between "the simulator" and "this particular plant".

nodes:       [{id, boundary, pressure}]
equipment:   [{tag, type, node_in, node_out, design: {...}}]
             [{tag, type, ports: {name: node | {node, phase, purpose, control?, direction?}},
               paths: [{from, to}], design: {...}}]
limits:      [{tag, variable, lo_lo, lo, hi, hi_hi, trip, deadband}]
controllers: [{tag, pv, sp, out, mode, kp, ki, kd, action?, tunable?}]
interlocks:  [{tag, condition, delay_s, actions, reset}]

Each top-level key is owned by a different milestone, which is deliberate — two agents editing different keys of the same file conflict only on whitespace.

Ports. A ports entry is a node-id string (untyped) or a typed object carrying node, phase, purpose and optionally control (T3-6, T3-7). Configured-port mode is ruled but not yet implemented: docs/ADR_0002_TYPED_PORTS.md Amendment 3 lets a device class that explicitly opts in — only Vessel — take its structural port set from configuration. Every entry is then a typed object carrying direction (inlet or outlet), and the loader builds the ports in config order. With no direction anywhere the device keeps its fixed ports. direction on only some entries, or on fixed-port equipment, is rejected. T5-7 implements this.

C4State snapshotapp/engine/snapshot.py

The single object every consumer reads. The historian, the console, the trend API, the scoring module and the scenario engine all take this and nothing else. Freezing it is what lets the entire user interface and the whole game layer be built before the physics is finished.

{
  "sim_time": 1830.0, "speed": 1.0, "running": true,
  "equipment":   {"K-101": {...}, "P-101": {...}},
  "nodes":       {"N-01": {"pressure": 750.2}},
  "streams":     {"S-01": {"flow": 98.4, "temperature": 88.1}},
  "controllers": {"PIC-101": {"pv":..,"sp":..,"out":..,"mode":"AUTO",
                  "kp":..,"ki":..,"kd":..,"out_min":0.0,"out_max":1.0,
                  "tunable":true,"pv_unit":"psia"}},
  "envelope":    {"K-101.outlet_pressure": {"band":"hi","since":1790.0}},
  "alarms":      [ Event ],
  "solver":      {"converged": true, "iterations": 4, "residual": 1.2e-9}
}

What an operator's browser receives is the operator view (decided 2026-10-05, built by T16-13): the same shape, with each equipment row cut down to the fields its device class lists as operator-visible - measurements, run status and the operator's own commands, never a fault flag, a malfunction-writable parameter, a design constant or a model internal. Server-side consumers - trips, alarms, scenarios, scoring, replay - read the full snapshot.

An equipment row also carries its device's solved points (decided 2026-10-09, built by T9-5): a device in exactly one branch gains flow, inlet_pressure and outlet_pressure, composed by the engine from that branch and its two nodes. The device itself still holds none of them (C1). A configured point that names no published number is refused when the plant is built.

C5HTTP APIapp/api/

One action endpoint, not a route per control. This is why it matters: every operator input flows through a single chokepoint, so the action log, replay and scoring get built once instead of per-control, and app/main.py stops being the file every branch has to touch.

GET  /api/snapshot                  -> Snapshot
GET  /api/stream                    -> SSE of Snapshot
POST /api/action  {target, action, value}
GET  /api/trend   ?tags=&from=&to=&max_points=  -> {tag: [[t,v],...]}
GET  /api/trend/points              -> {points: [tag,...], limits: {tag: {...}}, max_tags, max_points}
POST /api/alarm/ack  {alarm_id}
POST /api/scenario/{load|start|abort}
GET  /api/scenario/result           -> ScenarioResult

A target is a device, an interlock or a loop (loops decided 2026-10-07, built by T16-14). A loop takes manual, auto, set_setpoint, set_output and, where configured tunable, set_kp, set_ki and set_kd. A device that a loop drives is commanded through the loop, never directly.

A trend tag is a point, <id>.<field> (decided 2026-10-07, built by T17-3): the same key the snapshot's envelope section uses, drawn only from what the operator view shows. A range outside the buffer returns what exists; max_points and the tag count are bounded and refused beyond the bound. A point's evaluated envelope limits ride on the points list (decided 2026-10-08, built by T17-4), keyed by point with the Limits field names, only for limits the engine evaluates. Each point's descriptor rides there too (decided 2026-10-09, built by T10-6).

C6Event recordapp/events.py

One shape for alarms, trips, operator actions and scenario events. A single shape means the debrief, the historian and the scoring module each need one parser, not four.

{"id": "...", "sim_time": 1830.0,
 "type": "alarm" | "trip" | "action" | "scenario",
 "tag": "K-101", "priority": "critical" | "high" | "low",
 "message": "K-101 discharge pressure HIHI",
 "data": {...}}

Alarm messages name symptoms, never causes. "Discharge pressure HIHI" — not "discharge valve stuck". This one rule is what makes diagnosis possible later, and it has to hold from the first alarm written.

A message names its point by the point's descriptor (decided 2026-10-09, built by T10-6): the operator's word for a published field, such as discharge pressure for a machine's outlet_pressure, from the operator view, the same words the trend shows beside the point id.

C7Alarm interfaceapp/alarms/

A pure function of envelope events and time. No plant access, which is what makes it testable in isolation on day one.

AlarmManager.evaluate(envelope_events, sim_time) -> list[Event]
AlarmManager.acknowledge(alarm_id, sim_time) -> None
AlarmManager.active() -> list[Alarm]

states: NORM -> UNACK_ACTIVE -> ACK_ACTIVE -> NORM
                            \-> UNACK_CLEARED -> NORM
C8Malfunction and scenarioapp/disturbances/, app/scenarios/

The structural guarantee that the game layer cannot bend the physics.

Malfunction(target_tag, parameter, value, profile, start_condition)
Scenario(initial_condition, malfunctions[], triggers[],
         objectives[], time_limit_s, difficulty, seed)

A malfunction may only write parameters an engineer could change — a valve position limit, a heat transfer coefficient, a line resistance, an instrument bias. It may never write a solver output. A stuck valve sets a position limit; it does not set flow. Task T13-5 enforces this with a test.

Startable right now

Computed live from task status: every task whose dependencies are all complete and whose own status is still Not Started. Independent tasks can be handed to another agent immediately; core tasks belong on the main path with one owner.

Critical path

cannot slip without moving the date

Everything else in this plan has float. This chain does not. Each link is a piece of shared architecture whose shape every downstream task is written against, so a week lost here is a week lost at the release, not a week absorbed somewhere else.

What makes this the critical path rather than just the hard work. The chain is defined by contract ownership, not by difficulty. Each of these tasks publishes a shape — a base class, a snapshot, a graph, a solver output, a trip action, a scenario lifecycle — that other branches import and cannot be written without. A late satellite delays one feature. A late contract delays every branch that was waiting to be written against it.

Float in the plan: the critical chain as scheduled lands its last item at Checkpoint H on 17 December, one day before release, but the hardening window from 7 December absorbs slip ahead of it. Practical buffer is about one week, all of it sitting between Checkpoint G (9 December) and the release. Spend it on defects, not on features.

The three places this plan is most likely to slip: the network solver failing to converge on a topology that looks reasonable (T4-2); level-to-hydraulics coupling oscillating once the solver and the integrator disagree about timescale (T5-2); and the console integration at M16, which is the first time every subsystem is exercised together by a human rather than a test. Each of those has been given a wider window than its task count suggests.

Ownership rules that keep the merges clean.

• No satellite branch may modify app/equipment/base.py, app/engine/ or app/plant/topology.py. Those are spine-owned. A satellite that needs a change there raises it with the spine owner instead of making it.

• app/main.py is the highest-conflict file in the repo until the single action endpoint (C5) lands. Exactly one branch touches it at a time.

• app/config.py is append-only, one clearly-headed section per module. Never reorder it.

• static/compressor.js is frozen — it is replaced wholesale at M16. Do not invest in it.

• Satellites rebase onto main after every checkpoint. Main is never merged backwards into the spine.

Parallel agent assignments

Which branches can be handed to a separate agent, when each is allowed to start, and where it must merge. Model level is a judgement about blast radius and ambiguity, not about task size — a small task that redefines a shared shape is an Opus task, and a large task with a written spec and a test list is not. The general rule — Sonnet implements and executes, Opus decides — is stated once, in the Agent model guidance section of AGENTS.md; the assignments below apply it per task.

Opus

Work where the shape is the deliverable and getting it wrong is expensive to undo: the equipment contract, the snapshot, the solver, level–hydraulics coupling, the malfunction boundary, integration reviews at each checkpoint.

Sonnet

Everything else, which is most of the project. Feature work against a contract that already exists — equipment models, PID and modes, alarm management, the HTTP layer, the console, trends, scenario authoring — and the narrow, fully-specified work with an obvious done condition: the clock, the RNG, the ring buffer, the isolation guard, CI wiring, hygiene, requirements, documentation.

Thirteen branches can be handed out on day one — before a single line of the new architecture exists — because every one of them is a pure algorithm with a written specification and no plant dependency. That is the whole return on writing the contracts first.

The limit on parallelism is review, not branches. Every satellite eventually merges into a spine one person owns. Running more than roughly five or six live branches at once means the integration queue, not the implementation, becomes the bottleneck — and integration is the part that cannot be parallelised.

Schedule

18 September → 18 December 2026

Thirteen weeks, drawn from the same milestone data as the checklist above — the solid portion of each bar is real completed work, so the chart reports progress rather than intent. Dashed arrows are dependencies: where one exists, the bar cannot start until the arrow lands.

Reading the overlaps. Bars that overlap are not a scheduling error — they are the plan working. M9 envelopes, M10 alarms, M16 console and M17 trends all begin weeks before the physics they display is finished, because each starts as a pure module built against a frozen contract and only needs the plant at the end. That overlap is the difference between thirteen weeks and twenty-five.

Reading the gaps. Where a bar starts later than its dependency ends, the gap is deliberate float. Where a bar starts before its dependency ends, the early portion is contract-only work that does not touch the dependency's output.

Where the plan protects itself. Two windows carry no new features: hardening from 7 December and deployment from 14 December. If work slips, it eats those windows and the release still happens on a smaller feature set. If features are added into those windows instead, the date is gone — that is the single most likely way this schedule fails.

Keeping this current: change a task's status from the dropdown and it saves for everyone immediately. Use the note field inside a task to record who owns the branch or why it is blocked. Milestone and overall progress recalculate on their own.

A task marked Blocked still shows its dependency chips, so the real blocker stays visible rather than living in someone's head.

Schedule and checklist are one dataset. Milestone dates, the critical path, agent assignments, the deferred list and every bar in the Gantt chart are generated from the same milestone and task definitions as the checklist above. Change a status and the chart moves with it; there is no second copy of the plan to fall out of date.
